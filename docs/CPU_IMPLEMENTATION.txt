タイムポーカー CPU 実装記録
更新日: 2026-11-15

目的
- 「初学者」CPUを先行実装する。
- 後続の「受験生」「専攻生」「歴史学者」を同じAPIに追加可能にする。
- 人間らしい曖昧さを残し、完全回答・常勝のCPUにはしない。
- Firebase無料プランを前提に、CPU判断をホスト端末内で行い、Cloud Functions等を必要としない設計を守る。

強さの定義
- 初学者: 世界史の通史は学んだが年号記憶は曖昧。出来事ごとに思い出せる時と大きく外す時がある。
- 判断には確率的な迷いを入れる。毎回最善手を選ぶ仕組みにはしない。
- 待ち時間も一定にせず、考えているように見せる。

共通API案（novice-cpu.js）
- TimePokerCPU.create(level, rng)
- answer(question, minYear, maxYear): 年号を推測
- action({toCall, points, confidence, currentBet}): check/call/fold等を判断
- thinkDelay(): 行動までのばらついた待ち時間
- 難易度固有値はtier profileへ分離し、共通ロジックを再利用する。

実装済み
- 初学者の年号推測に記憶率、推測誤差、年代感覚のずれ、上下限を設定。
- ポーカー判断に自信の低さ、コール率、低確率のブラフ、可変思考時間を設定。
- Firebase SDKへ依存しない独立ファイルにした。

未完了 / 次の作業

- ロビーにCPU追加と強さ設定を追加し、CPUを参加者として表示する。
- ホスト側の進行処理で回答・ベット・準備完了・ショップ操作を生成する。
- CPUの回答を人間の非公開回答と同じく扱い、プレイヤー向け公開データに早期露出しない。
- 1人＋CPUで開始できること、2〜5人上限、抜けたCPUや再戦の扱いを確認する。
- Firebaseルールは最小権限のまま。CPUを認証ユーザーとして偽装しない。

重要な取り決め
- CPUはブラウザ内のローカル処理。外部AI API、Cloud Functions、定期通信は使わない。
- Firebaseの匿名認証UIDをCPUに偽装しない。ホストの正規権限経路でCPU状態を管理する。
- 問題難易度（基礎〜ヘル）とCPU知識階級（初学者〜歴史学者）は別軸とする。
- まだゲーム本体には接続されていない。現在は判断エンジンの初版。

CPU性格・ネームドCPUの将来設計

設計原則
- 人格値は正解率の単一スライダーに畳まず、独立した確率パラメータとして持つ。CPUの個性と強さ（知識量）は別物として管理する。
- CPUごとに対局開始時のseedを決め、回答・待ち時間・行動の揺れを再現可能にする。同じCPUが毎回同じ行動をすることは避け、seedは対局ごとに変える。
- 正解年をそのまま答えさせず、記憶の断片、年代幅、分野相性、質問難易度を使って見積もる。高難度ほど記憶誤差を広げるが、完全なランダム回答にもならない。
- 決定論的に最善手を選ばず、候補行動ごとの期待値に性格重みとノイズを加えて選択する。

性格パラメータ案（0〜1）
- memory: 年代知識の精度・記憶の再現性
- intuition: 年号を大まかな時代へ寄せる勘の鋭さ
- caution: 賭け・危険行動を避ける慎重さ
- aggression: ベット、レイズ、難問への挑戦を好む度合い
- curiosity: アイテムを使って情報を得ようとする意欲
- thrift: 強力なアイテムを後の局面まで温存する傾向
- resilience: 目隠し・油・減点などの影響下でどの程度推測を崩すか
- adaptability: アイテムや相手の行動を観察し、次の判断へ反映する度合い
- variability: その場の迷い、ミス、気分の揺れの大きさ

アイテム意思決定
1. 使用可能な時期・対象・残数・所持状況で候補を絞る。
2. 情報獲得、回答精度補助、相手妨害、得点倍率などの目的別効用を評価する。
3. curiosity/aggression/caution/thriftに基づく重みと乱数で使用・温存・見送りを選ぶ。
4. 受けた効果はCPU状態へ明示的に記録し、blind/oil/scorePenalty等を回答誤差や行動 confidence に反映する。効果が消えるタイミングで状態も解除する。
5. CPUの内部推測・パラメータは他参加者に公開しない。公開されるのはゲーム規則上の回答や演出だけ。

ネームドCPU
- 共有する定義形式: id/name/tier/personality/voiceStyle/itemPolicy/portrait(optional)。
- 初学者〜歴史学者の知識profileを選び、その上に固定の性格ベクトルを重ねる。名前ごとに知識の誤差と性格の違いを持たせる。
- 最初は固定プリセットとして同梱し、ユーザー作成・Firebase保存は後段にする。無料プランのDB読み書き回数を増やさない。
- バランス調整用にローカルシミュレーションで回答誤差、アイテム使用率、勝率を測り、強すぎるプリセットを抑える。

2026-11-15: CPUのFirebase書き込み拒否と複数人対応の修正
- ポーカーのCPU行動要求はホスト端末が代理記録する設計だが、requests配下の検証がuid=auth.uidを必須にしていたため、CPU uidでのベット等がPERMISSION_DENIEDになっていた。登録済み cpu_ UIDに限り、ホストが代理記録できる検証へ変更。
- ready/bet/item/shopの種類、行動内容、金額など既存の検証は維持。CPU登録 roster の存在も必須にし、複数CPUの行動を引き続き個別のUIDで処理できるようにした。
- ベーシック/サバイバルのCPU回答は回答年を符号付きの西暦に揃えてから推測するようにした。BCE問題で正答年を誤って正数として扱う不整合を解消。回答は各ラウンドのFirebaseルールと参加者rosterに照合してホストが保存する。
- Firebase Consoleへdatabase.rules.jsonの反映が必要。Cloud Functions等の追加バックエンドは不要で、Firebase無料プランの構成を維持。

2026-11-15: 性格パラメータ、CPUアイテム判断、ネームドCPU JSON
- 通常CPUにも記憶力、時代感覚、攻め気、慎重さ、好奇心、温存傾向、迷いの7項目を設定できる画面を追加。これらは年号回答の誤差、思考時間、ベット判断、アイテム使用確率と選択重みに反映する。難易度tierの知識精度とは別軸のままにする。
- 初学者の既定値は中庸かつ不確実さを残し、神託など強いアイテムを毎回使う決め打ちはしない。レーダー・世紀の灯は推測幅を絞り、目隠し・油瓶は誤差を広げる。追い風札・おにぎにぎ・狂戦士・えごま油瓶の得点効果は既存の採点経路へ接続する。
- ベーシック、サバイバル、ハーフアンドハーフではCPUごとの所持品を初期化し、選択されたアイテムをCPU自身が判断して使用する。ポーカーでは質問・回答・覗き見・賭けの場面で所持品を選び、既存のCPUリクエスト処理へ渡す。複数CPUにも同じ実装を再利用する。
- CPUの強さ・性格値は公開metaへ置かず、ホストだけが読める rooms/{room}/cpuProfiles に保存。ポーカーは既存のホスト専用CPU状態に保持。
- database.rules.jsonにホストから登録済みCPUの所持品とアイテム効果を記録できる経路を追加。Firebase Consoleへのルール再デプロイが必要。追加バックエンドはなくFirebase無料プランの範囲。
- ネームドCPU定義を named-cpus.json（schemaVersion 1 / profiles配列）へ分離。named-cpu-converter.htmlでCSV読込、列・難易度・性格値を検証し、同形式のJSONを保存できるようにした。

2026-11-15: Firebase Auth復元とロビー開始状態の再設計
- Firebase初期化直後にcurrentUserを確認して匿名ユーザーを新規発行する競合を防ぐため、authStateReady()の完了を待ってから既存UIDを取得する。browserLocalPersistenceを設定し、対応できない環境では既定の永続化へフォールバックする。接続初期化Promiseを共有し、同時呼び出しでも認証を重複させない。

2026-11-15: CPU応答の停止防止、買い物、知識段階の再設計
- ベット停止の直接原因: 同じターンの処理済みキーをFirebaseへの保存・検証より先に確定し、賭け金不足などで行動が受理されなくても再試行を永久に抑止していた。キーはホストがリクエストを記録した後だけ確定するよう変更。賭け上限・最低レイズ額を満たさない判断はコールまたはオールインへ補正。
- ベットの考慮時間を最大約1.5秒に制限し、各ターンには5秒期限を設定。期限切れはホストがフォールドを記録して次へ進めるため、CPU/通信の停止で進行を止めない。
- ズバリ演出の完了待ちは人間プレイヤーだけを対象に変更。CPUのみが正解した場合、動画再生の終了通知を待たずに次へ進む。
- 非ネームドCPUの性格は一度だけ生成し、全8項目を0.28〜0.72に制限。買い物傾向を独立した性格パラメータとして設定でき、ポーカーショップでランダム販売品を買う確率に反映。所持枠/価格も判断し、買わない場合はショップをスキップする。
- 受験生/専攻生/歴史学者の知識は、基礎・標準・発展・超発展・ヘルごとの習熟率で段階化。上位ほど難問でも推定幅と正解率を改善。ネームドは従来どおり個別の極端な性格を持てる。
- Firebase機能やバックエンドを追加していないため、無料プランの利用形態を維持。既存Realtime Databaseルールを再デプロイする追加要件なし。

2026-11-15: ネームドCPU管理画面と敗北演出、ポーカー②の回答修正
- 回答結果描画で allHits を参照する前に定義していなかった例外を修正。全正解者と動画待ち対象（人間）を別々に持つ。
- ポーカー②（年号回答）では、CPUの回答前に所持品読み込みを試みて回答サイクルが失敗しうる順序を解消。回答を優先し、アイテム確認をこの段階では行わない。回答準備状態を先に保存してから回答を書き込むことで、回答イベントによる場面進行を古い状態で上書きする競合も防ぐ。
- named-cpu-converter.htmlをCSV変換からJSON直接管理へ変更。既存JSONを自動読込し、手動読込、追加、編集、削除、JSON出力に対応。アイコン画像と敗北画像は縮小してJSONへ格納し、Firebaseには保存しない。
- 名前付きプロフィールIDを参加者rosterに保持し、ゲーム中の一覧・結果に登録アイコンを表示。敗北時はJSONのdefeatImage/defeatLineを使った専用画面を表示する。複数人の演出は一枚のモーダル内で順番に表示し、重ねない。
- 敗北演出はベーシック、サバイバル、千人斬り、ハーフ個人/共同、タイムポーカーの最終結果で順位/生存状況に応じて表示する。

2026-11-15: 勝利演出、召喚コード、戦略性とアイテム妨害精度
- ネームドCPU JSONに勝利画像・勝利コメント欄を追加。敗北演出と同じモーダルで、勝者を先に、敗者を後に一人ずつ順番に表示。重なって開かない。
- ネームドCPU管理画面からプロフィールごとに召喚コードを設定可能。SHA-256の照合値だけJSONに出力し、コード平文は保存しない。CPU設定欄では未解放プロフィールを隠し、正しいコードで解放すると選択肢に追加。解放状態はコード照合値とともにブラウザー内へ保存。
- 静的配布のゲームではJSONと照合処理を解析できるため、召喚コードはゲーム内の解放キーであり、サーバー認証と同等の秘匿/アクセス制御ではない。
- CPU性格に「戦略性」を追加。所持アイテムの使用判断重みを高め、確信度に応じて回答補助を選び、攻撃系は優勢な相手を狙いやすくする。ポーカーでは高ポイント相手、サバイバルでは生存数/HPの多い相手、通常戦では過去得点上位を脅威として扱う。
- 目隠しは黒塗り率、油瓶はアイテム段階ごとの強度をCPU推論へ渡す。影響を誤差幅だけでなく記憶/認識確率と完全一致率にも適用し、上位tierでも濃い妨害を受けると正答率を下げる。ポーカーの出題前妨害も現在ラウンドへ反映。
- 実装は静的JSONとRealtime Databaseを継続し、画像・コード・解除情報をFirebaseへ追加保存しない。

【2026-11-15追補：回答待機とアイテム反射】
ベーシックのホスト判定は、参加者名簿にある全員の年号回答が揃うまで reveal へ進まない。時間切れ後もCPU回答処理は継続し、回答イベントを受信した後にのみ判定する。
自縄自縛は通常モードの既存itemEventsを読み取り、同じモード・問題番号の反射可能な攻撃から防御者の対象分を取り除き、攻撃者対象の派生効果を表示側で生成する。派生効果は反射済みフラグを持つため再反射しない。ポーカーは別の状態機械なので、host上で受けた負の効果を記録し、盾使用時は対象側の状態を再計算して発生元へ一度だけ移す。文明の利器は脱落状態の発生元へ反射する。

【2026-11-15追補：アイテム使用セリフと回答補正】
